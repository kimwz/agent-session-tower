# Development

## Run from source

Node.js 22.x >=22.22.3, 24.x >=24.15.0 or 26.x >=26.0.0, npm, and Git are required. The supported-floor SQLite matrix verifies macOS arm64 and Linux x64. Windows, macOS x64, other architectures and new Node majors remain unverified. `server/storage/runtime.ts` owns the final actual SQLite/API verdict; engines alone cannot grant support.

```sh
git clone https://github.com/kimwz/agent-session-tower.git
cd agent-session-tower
npm ci
npm start
```

`npm ci` installs dependencies and builds the server and web UI through the `prepare` script. `npm start` opens the browser at http://localhost:8000.

```sh
npm run dev
npm run build
```

`dev` runs the TypeScript server and serves the built UI without opening a browser. Rebuild after editing the client.

## Check changes

```sh
npm run check
```

This runs TypeScript checks, the test suite, and a production build. Tests use temporary session records and test processes; HTTP tests open local loopback ports.

### Keep live checks out of personal session history

A temporary working directory does not isolate native session storage. Codex writes conversations under `CODEX_HOME` (normally `~/.codex`), and Claude Code uses its configuration directory. Tower discovers those records, including conversations created by a smoke test.

Reviews, helper agents and live native checks use the existing Claude/Codex CLI login on this computer. Do not require a separately authenticated test profile, a new login or Vault access, and never inspect or copy authentication values. Keep temporary working directories, fixture data and Tower state separate from personal work; this does not require changing authentication homes.

Reviews and investigations that return one result are one-shot helpers by default. Use read-only/plan mode where supported, query Tower's configured model role with `models_get` or `agent-session-tower models args <role>`, and disable unnecessary tools, MCP servers and children. Separate CLI runs use `claude -p --no-session-persistence` or `codex exec --ephemeral`; close Codex stdin with `< /dev/null` when passing the prompt as an argument. An explicit owner/project request for a persistent helper takes precedence. Save the final result, success/failure or partial-result status, reviewed commit and artifact references in the parent/task record before releasing the helper, without duplicating its entire reasoning/tool transcript.

The persistent parent creates any helper worktree and retains its creation/ownership evidence; a nonpersistent helper uses the supplied folder rather than creating its own worktree. Never detach review processes (`&`, `nohup`, `setsid`, `disown`); wait or use the execution tool's own background support. Native Agent/spawn tools may not provide a nonpersistent option: do not invent one. Check child record handling independently, because an ephemeral parent does not guarantee ephemeral descendants. Residual persistent children use the separate retention policy; do not delete native history manually.

A native feature check that needs persistent sessions records its exact test session IDs and closes only those through Tower afterward. Close session is hide-only and preserves native records; it is not an explicit retention archive request.

`isolatedSmokeEnv` in `scripts/native-smoke-env.ts` preserves the current CLI environment by default. The optional `TOWER_SMOKE_CODEX_HOME` and `TOWER_SMOKE_CLAUDE_HOME` overrides remain available for an already configured test home; they validate separate storage and reject storage symlinks. They are not prerequisites, and the helper does not set CLI nonpersistent flags: the caller must use the supported execution option or track persistent test IDs. Do not copy personal credentials or symlink personal session directories into an override home.

If a check has already created personal history, use **Close session** in Tower to hide the specific test conversation. This preserves its native history and allows reopening it from **Closed sessions**. Do not hide all temporary paths: users may intentionally work in them.

### Session retention: current support and safety limits

The managed instructions in `server/agent-guidance/guidance.ts` make separate one-shot review/investigation CLI runs nonpersistent by default. This is guidance for agents, not a guarantee that every external invocation or native Agent/spawn descendant is nonpersistent. Keep the final result in the persistent parent/task record; native tools without a supported nonpersistent option leave records for the retention policy to observe.

`server/sessions/retention/policy.ts` owns the project parent limit and child expiry rules: the most recent 20 user parents per verified logical project, and children seven days after the latest work ends. Known-ended existing children use that work timestamp; unknown-ended children require seven continuously inactive days. Parent-limit migration grace remains separate. An old `closed-sessions.json` ID does not become an immediate archive request. **Close session remains hide-only.** A separate explicit retention archive request applies only to a proven inactive child. Running, queued, scheduled, approval/result-waiting work and needed ancestors stay protected. Claude children also remain protected while their parent or needed ancestor is live. The observer uses latest event ordering and file revisions, not a stale completion or file mtime alone.

Native cleanup means moving eligible records out of the ordinary history and Tower scan, while retaining recoverable originals. Codex uses `thread/archive` through a dedicated unloaded maintenance app-server; it does not call `thread/delete`. Native archived records and the paginated history database remain necessary for native `thread/unarchive`. Claude uses journaled, same-filesystem moves into private raw cold storage and restores without overwriting a new hot source. Each member has durable intent and confirmation so partial subtree moves can be retried. A live writer, incomplete inspection, changed source or new hot record prevents cleanup or marks a conflict; it does not authorize deleting either version. Tower reserves maintenance candidates against new queued launches instead of cancelling work. External provider activity can still conflict with maintenance and must be detected conservatively.

Tower excludes confirmed cold records before file stat/read/parse and loads that registry before its first session scan. A restored or changed record can reappear. Optional compressed transcript exports are separate from native cold confirmation: missing or corrupt exports report `backupError` without claiming that a retained native original is lost. **A JSONL export alone is not a complete, independent Codex native backup**, especially for paginated history. External imports never acquire local native ownership merely by supplying member paths. Encrypted Tower settings export and R2 settings backups do not include cold session bundles. Preserve native archive/database or raw cold storage separately when recovery is required.

The worker serializes maintenance, waits for outstanding operations during handoff, and never cancels turns or terminal shells on a web disconnect. Startup inspection failure reports retention unavailable while preserving core execution and records. `RetentionArchive.create` has streaming/file-count/byte budgets; optional exports can fail independently of a successful native cold move. Cold/native archive storage is retained and has no automatic capacity expiry: reduced hot scan load is not equivalent to disk space reclaimed, and duplicate exports can increase disk use. Cold metadata inspection has a 20,000-member batch budget; exceeding it reports incomplete observation and defers cleanup while ordinary hot discovery continues. Native databases, raw cold originals and the ownership journal have no automatic capacity limit. Monitor their growth separately; this release does not promise unbounded cold-history scaling.

`server/temporary/directories.ts` records exact ownership and identity for newly allocated private MCP/PTY directories. Normal cleanup is awaited; the bounded worker collector protects active consumers and open paths and pauses for handoff. Legacy cleanup is limited to old, empty, source-proven fixture directories, rechecks identity and activity, and uses nonrecursive removal. It preserves nonempty unknown directories, existing runner/socket roots and unrelated caches. Test fixtures retain canonical runner sibling paths while their root exists, close clients and hosts first, then remove those exact siblings and the fixture root without recreating them.

### Voice streaming diagnostics

Speech starts from a readable sentence while the master turn is running; completing the turn flushes only its remaining text. The host persists bounded measurements in `<state-dir>/master/voice-timings.json`: run/turn IDs, reply observation times, first sentence flush, per-part TTS start/first byte/completion, say transmission, and page progress. `firstAt` and `completedAt` are native events observed by the worker. `nativeEnd` is the run's completion time; `end` is the voice follower's completion time. Aggregate `delta`/`completed` retain the first values observed in a snapshot; reply records preserve each message's times.

Each bounded TTS part completes before its independent say is sent, so the MP3 response has an exact `Content-Length`. This waits for that part, not the reply or native turn's completion. Parts retain reply order and each requires its own terminal playback ACK. A resumed response advertises the remaining body length. This avoids the unknown-length MP3 startup stall reproduced with WebKit; the page also requires meaningful media-clock progress before reporting playback as started or completed. The normal watchdog and bounded recovery remain in place.

The page reports receipt/queue gate, each source and play attempt, play promise results, media-clock progress, waits, resumes, retries and ended events separately from the terminal playback ACK. Promise resolution or a tiny positive clock value is not evidence of sustained or audible output. A progress report never completes or retries a say. Progress `at` is the host's receipt time and `elapsedMs` uses the page's monotonic clock since receipt of that say. `attempt` distinguishes a replaced source; a late old promise has no snapshot of the new source. A bounded history retains the first 16 events and latest 48, with a drop count, so later progress no longer overwrites the only retry/wait evidence. Terminal ACK receipt and its page elapsed time are recorded during settlement, independently of progress HTTP arrival order. Legacy `play` is an estimate (`say` plus that page delay) and excludes transmission time.

Each generated audio request ID links its live MP3 to host and web relay request/first-write/bytes/end/close measurements, including a resume offset. These are server writes, not browser delivery or decoding times. Normal EOF and a subsequent close are distinguished from a cut stream. Records are bounded and omit speech text, audio, credentials, arbitrary URLs, headers and exception messages. Missing events or dropped history are not evidence of success. The original browser's network/media state and the owner's output device remain necessary to establish audible playback.

For a real media regression without native providers, personal microphones or new TTS calls, supply an existing nonpersonal valid MP3 and an installed Playwright module with WebKit (or select `chromium` or `chrome`):

```sh
VOICE_BROWSER_MP3=/absolute/path/to/fixture.mp3 \
VOICE_BROWSER_PLAYWRIGHT=/absolute/path/to/playwright/index.mjs \
VOICE_BROWSER_ENGINE=webkit VOICE_BROWSER_PCM=1 \
node --import tsx scripts/test-master-voice-stream-browser.ts
```

The isolated browser uses synthetic microphone input and fixture Tower/TTS responses, but real HTMLAudio decoding and optional Web Audio PCM (`VOICE_BROWSER_PCM=0` keeps the raw media path). It verifies finite headers, progress and the first part's ACK while holding the run open, then checks residual flush, deduplication, cancellation and replay. Results are written to `tmp/voice-recovery/finite-browser-<engine>-<raw|pcm>.json`. Optional `VOICE_BROWSER_TTS_DELAY_MS=3000` (integer 0–5000, default 0) sends the second fixture part's first bytes immediately and delays its remaining body and EOF. It measures the synthesis gap, calls public `VoiceSession.listen()` with silent synthetic media during that gap, and verifies that the microphone gate closes for the next audio. Delayed results use a `-delay<ms>` suffix; default checks are unchanged.

## Standalone executable

Building a standalone executable requires **Node.js 26.x >=26.0.0**. It produces a binary for the current operating system and architecture, with the Node runtime, server, and web assets included.

```sh
npm run build:executable
npm run test:executable
./artifacts/agent-session-tower
```

Running the resulting executable does not require a separate Node.js installation. Claude Code or Codex must still be installed and signed in to create or continue work. The macOS build receives an ad hoc signature; it is not notarized. The build also writes a SHA-256 checksum.

If the builder cannot locate the Node.js license beside the installed runtime, set `AGENT_MONITOR_NODE_LICENSE` to that license file. The legacy variable name is retained for compatibility. Embedded third-party notices are served at `/THIRD_PARTY_NOTICES.txt`.

## Source map

| Path | Purpose |
| --- | --- |
| `bin/` | CLI entry point |
| `server/` | Native session discovery, process status, local API, and queued CLI work |
| `client/` | React UI and graph canvas |
| `shared/` | Shared data contracts and session logic |

A Node HTTP process serves the API and built React UI. A separate detached execution worker owns provider connections, queued work, approvals, and Auto Prompt routing; terminal shells run in a separate terminal host (see [Web restart and execution worker](#web-restart-and-execution-worker)). The web process reaches both through authenticated owner-only local sockets; stopping the web process does not stop work or close shells. Server-sent events update the browser. No database or hosted backend is required. The graph uses React Flow.

### Browser workspace

Project editor/terminal controls open a resizable workspace overlay on the same authenticated page, to the left of chat when it is open. The minimum width is 420px, limited by the viewport; screens without enough horizontal space stack workspace above chat. Direct `/?workspace=<absolute-directory>&tool=editor|terminal` URLs remain available. CodeMirror edits UTF-8 files up to 2 MiB, with revision checks and atomic saves; the explorer lists up to 2,000 entries per directory and skips symbolic links. xterm.js connects to an interactive `node-pty` shell through authenticated SSE and token-protected input/resize requests. Each terminal tab owns its own shell (up to eight per workspace). Closing a tab stops its shell; hiding the panel keeps shells running. Active shells survive web disconnects and restarts; only an explicit tab close or shell exit ends them. The browser tab remembers the terminal tabs and their IDs for reconnecting. Exited terminal records are cleaned up after 30 seconds.

`node-pty` uses native bindings. Platforms without a matching prebuild need a C++ build toolchain and Python during dependency installation. Standalone builds embed the matching bindings and extract them into a private temporary directory when the first terminal starts. The PTY smoke test uses `/bin/sh` with an isolated HOME and never launches a native agent provider.

## Master heartbeat

`server/master/heartbeat.ts` owns the master's periodic inspection and private `master/heartbeat.json` ledger. It runs inside the singleton master host, independently of the web connection. The existing master follower remains responsible for ordinary delegated-result delivery. Heartbeat uses the same followed work, with selected current progress and bounded transcripts, and calls `runAutoPromptModel` without tools or persistent native sessions. It does not diagnose a stall from `working` or elapsed time alone. A tracked native request is matched by exact normalized prompt (including delivered steering and Tower attachment suffix) in the bounded page plus `previousUser`, not by comparing its recording timestamp to queue admission. Update/permission continuations follow their same-session run ancestry (at most 32 hops): a provider system notice may retain the original native user request, while a user-projected notice must match its actual continuation. Only genuine delivered requests supersede earlier requests; trusted permissionNotice/updateWrapUp provenance distinguishes internal steering notices (also retained by the shared run projection), not their text prefix. Missing/cyclic/foreign-session ancestry, any explicit owner stop in that work’s managed continuation/steering lineage, and unread/missing identity exclude the target. The same lineage stop check protects inspector, narrow tools, remote protection and final admission; a new independent owner task does not inherit a prior task’s stop. Changed native request IDs after an observation exclude even an identical follow-up; an identical external request before the first observation cannot be distinguished by prompt alone.

Master settings contain enablement, interval and inspection guidance. Models' `master.heartbeat` role uses `provider: "follow"` to dynamically inherit the **whole** `master.session` role; this role's stored provider picks are inactive while following. Choosing an explicit provider uses its dedicated pick; empty model/effort means the CLI's default. This does not copy the model selected in the current master conversation.

Checks and sending intents are saved before their effects. Overlapping ticks join one inspection, restart abandons interrupted checks without catch-up, and settings changes invalidate an in-flight result. Model failures remain internal until the next regular interval. No-op changes only the internal inspection status. Action recommendations are evidence-bound data sent once to the existing master, which assesses them under its existing authority and delegation paths. The settings UI shows recent inspection status and action audit; no-op produces no chat, voice or notification.

The authenticated master heartbeat header is internal admission data, never a public message-body privilege. The execution worker rechecks master idleness, the native/run watermark, and local target pending/owner-denied permissions, native approvals, latest owner stop and target existence immediately before inserting an action run, marks its origin as agent input, and refuses stale or duplicate checks. Web model `needsOwner` outcomes are adopted only when snapshot message count and last message match native detail; a final bounded snapshot rechecks these outcomes and native progress before sending. These model outcomes are a pre-send heuristic, not worker-atomic approval state. Remote target protection is a bounded REST check before delivery, not an atomic cross-computer transaction; the master must recheck that target before taking action. A worker without `heartbeatAdmission` support refuses these submissions. Evidence reads, model-role resolution, the one-shot model and recommendation dispatch have a shared 90-second action window. Durable local ledger writes and accepted-run tracking are deliberately drained in order, including after expiry: they do not dispatch further actions, and the next tick and host handoff wait for that drain. A stalled local filesystem can therefore delay drain/close; no new inspection or overlapping write is allowed. Racing an uncancellable fsync/rename would allow an older write to overwrite a newer claim. A write already sent is not cancelled at that deadline; its saved intent becomes uncertain and any late response is not replayed or processed. Uncertain delivery is not automatically resent; proven non-admission releases the evidence claim for a new assessment on the next regular interval, without immediate retries. An authenticated admitted heartbeat run keeps agent origin and receives only `heartbeat_read`/`heartbeat_correct`, scoped to its selected existing tracked assignments. The host verifies the live run capability, binding, original heartbeat root run and ledger action, selected assignment scope and current target protection; update/permission continuations preserve that same root and tool scope. Settings changes and host close invalidate unsent corrective gates immediately; already sent transport and durable records drain without replay. Local corrective admission rechecks the selected target latest run and native request timestamp, and remote protection includes the latest explicit owner stop; corrective attempts have durable check/target intents and are never repeated, including uncertain transport or restart. No general Tower API, session creation, Auto Prompt, settings, approval, UI, secrets or browser tools are attached by this heartbeat mode. Existing provider configuration remains under the master’s existing authority; this mode does not rewrite global provider MCP settings. Heartbeat input never releases an owner-stop hold or acts as owner approval. Regression fixtures live in `tests/master/heartbeat.test.ts` and the relevant master, model, HTTP and runner tests.

## Releasing

Every change reaches `main` through a reviewed pull request. A pull request that changes what Tower does carries its release; one that changes only documentation, agent instructions, tests, or CI has none and ships with the next release.

1. On the pull request branch, pick `x.y.z` above the version on `origin/main` (`git show origin/main:package.json`) and write the `## [x.y.z] - YYYY-MM-DD` section at the top of `CHANGELOG.md`, dated today.
2. Run `npm version x.y.z --no-git-tag-version` (`.npmrc` also turns off npm's own commit and tag). It runs `npm run check`, refuses to continue without that changelog section dated today, syncs the version the app reports, and rebuilds. Commit `CHANGELOG.md`, `package.json`, `package-lock.json`, and `shared/app-identity.ts` as `Release x.y.z`, push the branch, and wait for CI to pass.
3. Right before merging, `git fetch` and check:
   - `git merge-base --is-ancestor origin/main <head>` must succeed; otherwise merge the new main and revalidate the changed tree. The current tree has successful `Linux validation gate (Mac requires owner evidence)` (Linux) and `macOS (owner Mac)` evidence, and `validation (all platforms)` confirms the same clean input tree. Missing local results are incomplete, never an implicit pass. See the CI verification section below. No repository protection rule is currently configured; the merge operator must check these results.
   - `x.y.z` is above the version on `origin/main`, and `git ls-remote --tags origin vx.y.z` prints nothing. Otherwise, or when the branch conflicts with `main`, merge `origin/main` into the branch (never rebase a pushed branch). In a conflict keep `main`'s changelog sections and versions as they are, move your own section and version above them if needed, and repeat step 2.
   - The changelog section is dated today. Otherwise re-date it and repeat step 2 with `--allow-same-version`.

   A change of version or date alone needs no new review. After any new push, start step 3 again.
4. Merge with `gh pr merge <number> --squash --match-head-commit <head-sha>`. If GitHub refuses it (the branch changed or conflicts with `main`), go back to step 3.
5. `git fetch origin` and take the merged commit from `gh pr view <number> --json mergeCommit -q .mergeCommit.oid`. Check that `git merge-base --is-ancestor <commit> origin/main` succeeds, that `git show <commit>:package.json` has `x.y.z` and `git show <commit>^:package.json` a lower version, and that CI passed on that commit (`gh run list --commit <commit> --workflow CI`; the run can take a few seconds to appear, then wait with `gh run watch <run-id>`). Compare `<commit>^{tree}` to the paired Mac/Linux record. Only an identical tree permits reusing that original record and timing, then publishing both evidence statuses on the merged commit. A changed tree needs new Mac validation and matching Linux results before tagging. The Release workflow publishes before its own checks and service Towers install the latest release, so never tag a commit whose CI has not passed.
6. `git tag -a vx.y.z -m "Release x.y.z" <commit>` and `git push origin vx.y.z`. The Release workflow publishes the changelog section as the GitHub release notes.

If step 5 fails, do not tag, and never move or force a tag. If another pull request took the version first (the parent is not lower, or the tag exists), open a follow-up pull request that moves the version and changelog section above `main` and release that one; it needs no new review. If CI failed on the merged commit, fix it in a new pull request. Push release tags one to three at a time; GitHub starts no workflow for a push of more than three tags.

To deploy a Tower that runs from this checkout, update the folder it runs from once nobody else is working in it: `git pull --ff-only`, `npm ci` when dependencies changed, `npm run build`, then restart the web process only (see below).

A specific release can be run with `npx --yes github:kimwz/agent-session-tower#vx.y.z`.

A Tower running as the background service moves to the new release by itself within about 30 minutes. It waits up to 15 minutes for the Release workflow to publish the package. To move it at once, ask its own web server: `POST /api/tower/update` with an empty JSON body (the latest release) or `{ "version": "x.y.z" }`, sending the page token from `/api/bootstrap` in `X-Agent-Monitor-Token`. Computers it controls follow it right after.

Development and fixture instances should run with `TOWER_AUTO_UPDATE=off`. Tower from a checkout or npx never replaces itself; only the service does. Claude Code and Codex are updated only by the Tower on the default state directory.


### Web restart and execution worker

Restart the web PID only. Its shutdown closes HTTP streams and authentication sessions, but never sends provider cancellation or termination. The worker owns `runs.json`, `created-sessions.json`, and `auto-prompts.json`; only one worker may write them. Its separate lock is in `<state-dir>/runner-runtime/`. Local RPC uses a short Unix socket in an owner-only `/tmp/tower-runner-<uid>-<hash>/` directory plus a private random credential. This worker transport currently targets POSIX systems.

After the web server stops, running and queued work and approval waits remain live. Restarting with the same state directory reattaches without resubmitting prompts. Mutating RPC requests are not retried after uncertain transport failures. An incompatible worker is never replaced while handling work. The worker exits only after at least 30 seconds without a web client and with no active runs, routing jobs, or shells of its own (opened before the terminal host). Slack monitoring keeps the worker active.

A web process that attaches to a worker from an older build asks it to hand off; a newer worker (left by an update that was undone) is never handed back to an older web. The worker keeps serving, including Slack, until a moment when no run, routing job, Slack task in progress, or shell of its own is active. It then refuses new submissions for that instant, saves its state, records `runner-runtime/handoff.json`, releases its lock, starts the web build's worker, and exits. The web reattaches to that successor only with this record; any other worker change still requires a restart. A submission refused during the switch returns 503 and was not accepted, so it can be sent again. If no quiet moment comes for six hours, new Slack mentions are saved but left for the successor to start; running work is never interrupted. While the attached worker runs a different build from the web page, the header shows **Worker update pending**; features added since that build do not apply until the handoff.

Undoing an update can leave an older web on a newer worker, and features the newer worker dropped are missing then. A web before 1.131 cannot load its secrets UI from a 1.131+ worker, which no longer serves `overview`; restart the worker once nothing is running to go back. A newer web on an older worker (a pending handoff) still offers the vault's lock and unlock, reading its status from that worker's `overview`.

When the worker serves it (capability `forceUpdate`), the header also offers **지금 업데이트** (update now), `POST /api/runner/force-update`. It is the owner's explicit request, so it may stop turns. The worker records the handoff and starts an update drain: no queued turn starts (`pump()` waits beside the provider-update hold), the owner's messages are not inserted into turns waiting on background work, and Slack, triggers, GitHub, public agents and skills hold new work. Every running turn is asked through the normal insert path to wrap up; at the deadline (10 minutes) the turns still running are cancelled. When a turn the update interrupted ends — stopped by the deadline, or ended after its wrap-up request reached it — Tower queues its own continuation (`scheduled.resume: 'update'`, same origin, model, effort and required instructions) in that same step, replacing the agent's own wakeup; it runs before messages queued behind that turn. A turn the owner stops (in Tower or the Codex app), one that fails, and one that completed before any wrap-up reached it end as they are. Delegated work of a Slack or GitHub workflow is neither asked nor resumed: it is cancelled at the deadline with a reason and its coordinator hears the result on the next worker. Codex app submissions that have not started are taken back out of the app's queue. The handoff then waits only for live provider processes, routing jobs and work underway this instant (`transient()`), not for queued turns or workflows waiting on them. Queued turns accepted meanwhile are marked `keepQueued` in `runs.json`, and required instructions of turns still to run are kept in `run-instructions.json` (0600), so the successor restores them instead of cancelling them. A worker starts restored turns only after its tools, gates and limits are set up (`holdUntilReady`, `markReady()`). Trigger and public-agent watchers follow a turn into its update continuation (`continuedRun`). History keeps every unfinished run, runs a workflow still has to report (`retain`), and the newest 100 finished runs. If the handoff still cannot happen 10 minutes after the deadline, the drain ends and queued turns start on the current worker. The master agent follows a delegated run into its continuation. It is refused while a service update is still being verified. Regression checks: `tests/server/runs/runner-update-drain.test.ts` and the forced-update case in `durable-runner.test.ts`.

Owner-started Claude turns with outstanding background results can recover from an unexpected provider exit. Tower queues a continuation in the same conversation after 15 seconds (30 and 45 seconds on subsequent failures), preserving the origin, model and effort. Its persisted `scheduled.backgroundRecoveryAttempt` caps the chain at three retries. Recovery first asks the agent to inspect existing files and processes, rather than repeat the original request. Explicit cancellation, a newer instruction, a pending approval or unacknowledged steer, provider-reported errors, and the two-hour background wait limit do not trigger recovery. The ordinary scheduled-continuation admission checks also apply after a restart. Run output records the exit code/signal, whether Tower closed stdin, and pending-task counts; stderr is retained in the error. Regression checks use fake providers in `tests/server/runs/runner-background-tasks.test.ts`.

Terminal shells run in a separate terminal host (`--terminal-host`) with its own lock in `<state-dir>/terminal-runtime/`, socket and credential. Replacing the worker never touches shells. The web starts the host when a shell is opened; the host exits after 30 seconds with no shell and no web request. Shells opened in a worker from before the terminal host remain reachable through that worker until closed.

The worker, terminal host and master host keep their `/tmp` socket and credential alive while they run (`server/runs/endpoint-keeper.ts`): every 5 seconds a credential that a `/tmp` cleaner removed is written again with the same value, and files older than an hour are touched. Without it, a host that lost its credential still holds its lock, so no replacement can start and its clients are locked out.

The first upgrade from an older in-process runner needs a handoff or a fully drained old server: its old SIGTERM handler still cancels work. Do not start a new worker against the same state files while the old runner is writing them. Test with fixtures; never kill the old process merely to test restart behavior.

### Encrypted secrets

Owner secret management requires direct localhost or an explicitly configured authenticated HTTPS origin. Caller-supplied forwarded-protocol headers do not establish HTTPS.

Each saved secret has its own sharing, edited in **Settings → Secrets**: **GLOBAL** (every folder of every computer this Vault serves: this one and its trusted node peers), chosen canvas folders, or neither. A folder is a canonical identity, the Vault ID of its computer and its real path: the web resolves the page's folder key with `realpath` here, or asks a joined computer (`@<node>/<path>`) over its link (`/secret-folder`), only when that computer is trusted for secrets and advertises the link feature `secretSharing` (`server/secrets/folders.ts`). Saving a folder that is not one, or one of an untrusted or older computer, is refused with the reason; folders match only by exact root, so a sibling worktree is a folder of its own. Sharing changes carry a revision, and a stale one is refused. Besides sharing, the owner connects keys to one session from its chat: a connection allows every operation and field there until the owner disconnects it or the task ends, and a disconnection stops a key in that session whatever allows it, until the owner connects it again. The chat's paste field connects a value to the session as a temporary value that ends with its task, unless **Save to vault** keeps it, unshared, in this folder or GLOBAL. A key saved before per-secret sharing keeps following its rules, every rule now automatic and a rule's time limit counted from the task, until the owner edits its sharing; that edit takes the key, with its field selections, out of the rules and only it. A rule that names an edited key again can only come from an older build, so that key's GLOBAL and folder sharing is withheld until the owner saves it again. Listing and viewing never start a task, write the journal or claim an operation. Task lifetime is independent of model summaries and turn completion. Session archive and expiry revoke later use and clear temporary payload; a previously authenticated run cannot rebind to a replacement task. Lock, disconnection and web disconnect do not kill agents or terminals, and cannot recover plaintext already given to a consumer.

`server/secrets/` owns encryption, task/policy authorization, the consumer broker, remote proof and runtime tools. `shared/secrets.ts` contains public metadata/reference contracts. `SecretVault` uses a random 256-bit Vault key, a password wrapper derived with Argon2id (64 MiB, three passes, four lanes), and AES-256-GCM with fresh nonces and purpose/version/Vault-bound AAD. The Vault password is the **recovery password**; the Tower (login) password opens the Vault through its own Argon2id wrapper of the same key in `vault.json`'s `tower.wrappers` (at most two: the current one and one during a password change), named by the `credentialId` of the login credentials it was made for (a hash of auth.json's salt, not a secret) and bound to it by its AAD. Older builds keep the field through their saves. `secrets/vault.json` stores permanent encrypted records; `secrets/journal.json` separately encrypts temporary values, tasks with their connections and exclusions, value-free records of recent uses, and operation claims. Reads refuse symlinks and are bounded; writes use private permissions, exclusive temporary files, fsync and atomic rename. Journal-first commits preserve denial/pending state; persistence failure locks the service. A new execution worker starts locked, while a web reconnect retains the existing worker's unlock. Passwords belong only to owner control requests, not prompts, argv, provider environments or the generic operation ledger.

Use the run-scoped MCP tools (`secrets_list`, `secrets_run`, `secrets_compare`, `secrets_fingerprint`, `secrets_cli`). Lists return metadata, not values; while the vault is locked they come from `secrets/index.json`, a plaintext policy index (names, references, rules, sharing, tasks with their connections and exclusions, the computers GLOBAL covers; no values or keys) rewritten at every unlocked save and evaluated by the same `policy.ts` authorization, and any use fails with an unlock request. Each use handed to a consumer, and each one the reviewer refused, is recorded with its session (secret, operation, outcome, review; no value) on the computer that used it, and the session view shows the latest ones. The broker launches consumers without a shell and supplies only requested secrets through env, stdin or private files outside the project. Selected dotenv fields support env-bundle delivery; whole-file delivery requires all fields. It reauthorizes before spawn and masks bounded stdout/stderr before tool or CLI output. Internal equality and domain-scoped HMAC fingerprints require operation permission and use the same final authorization gate before computing their result. No raw-value read/export command exists. The operation journal gives a duplicate request its recorded result or an uncertain response rather than running it again.

Secret tools remain available for discovery when the current task actually needs credentials; ordinary turns receive no secret guide in their prompt. Tool descriptions explain reference discovery and consumer mapping, and tell agents to leave unrelated work and vault state alone. Only the owner's explicit connection to a session (a chat paste, or connecting a saved key there) opts into a fixed, value-free notice for each running native turn of that session that has the secret tools, whoever started it. Vault setup/unlock/lock, saved-value edits, sharing changes, disconnection, expiry and source availability changes remain silent; the broker still checks current authority at each use. A remote chat connection carries its committed target over the separately approved paired link before reading the session view; the receiving worker checks owner eligibility, exclusions and the current task ID. Notices coalesce and wait during approvals or another insert; an uncertain delivery is not resent. Idle sessions do not start a turn for a notice. The private block is hidden from Tower chat and never stored as a new run or user prompt; it can remain in the provider's native history. It contains no secret names, references, values or owner input and grants no additional permission. Desktop-owned conversations do not receive these inserts.

The CLI shares the MCP parser. Direct invocation requires the current run's authenticated `TOWER_SECRET_CAPABILITY` and absolute `TOWER_SECRET_STATE_DIR`; cwd, a native thread ID or a worker master credential never supplies a secret subject. These examples use references from `list`, not literal values:

```sh
agent-session-tower secrets list --json
agent-session-tower secrets run --env API_TOKEN='tower-secret://VAULT/SECRET@1#TOKEN' --operation-id request-1 -- node script.mjs
agent-session-tower secrets pipe --secret 'tower-secret://VAULT/SECRET@1' --operation-id request-2 -- node stdin-consumer.mjs
agent-session-tower secrets fingerprint 'tower-secret://VAULT/SECRET@1' --domain deployment
```

`run`/`pipe` need a stable `--operation-id`; retry with the same ID and do not automatically assign a new one after an uncertain result. The capability belongs to the secret MCP transport, not the provider's global environment. The consumer environment strips Tower credentials. Same-UID code and trusted consumers can read delivered plaintext; exact/escaped/encoded output masking does not prevent deliberate transformations, arbitrary file access or network disclosure. This is not an OS sandbox or a complete data-loss prevention system.

The owner page reads `GET /api/secrets/settings` (every saved key with its sharing, or a summary of the rules it still follows; no values) and `GET /api/secrets/session?sessionId=ID[&nodeId=NODE]` (what that session may use and why, the keys the owner may connect, its recent uses, the sources that could not answer, and the sources waiting for an update). A session view never starts a task; a state that stays until the owner acts (no Vault, an ineligible or closed session) is marked `permanent` so the page stops polling. Changes are `POST /api/secrets/sharing`, `create`, `session-connect`, `session-disconnect` and `session-reallow` (lifts this session's stop on another source's key, which still decides its use), beside the Vault actions; the web turns folder keys into folders before the worker sees them, and a joined computer's session is verified over its link. While the attached execution worker predates the capability `secretSharing`, these routes answer 503 with `code: 'worker-update-pending'` without calling it; the settings and session views carry only the vault's status read from its `overview` (`workerUpdatePending`), so lock and unlock still reach it, and the snapshot carries `secretSharing: true` once the worker serves them.

The owner sees and edits values only after unlocking **value viewing** with the Tower password, from a signed-in browser. `POST /api/secrets/view-unlock {password, recoveryPassword?}` checks the password as a sign-in would (a wrong one counts toward the IP block; `401`/`403` with `code: 'login-required'`), then asks the worker to open a locked Vault with the wrapper of the current `credentialId`, or to check (and, when missing or stale, make) that wrapper on an open one; a locked Vault without a working wrapper answers `409 needs-recovery` until the page sends the recovery password once, which opens the Vault and wraps it for the Tower password. A loopback page without a sign-in signs in here and gets the cookie; loopback alone never reads a value. The web keeps each sign-in's grant in memory (`server/secrets/view-grants.ts`) with the worker's lock generation, for 15 idle minutes; `POST /api/secrets/value {secretId, expectedVersion}` and `value-update {secretId, expectedVersion, value|content}` need it (`403 view-locked` otherwise, also once the worker's generation changed) and refuse a version that moved (`409 conflict`); the worker checks the generation in the vault's serial queue, behind any lock or open queued first, and the compare and the change are one serial save. `view-lock`, a Vault lock, sign-out, a login change and a web restart end grants. Settings answers carry `valueView`, and settings and session answers carry `status.towerPassword` (`ready` or `missing`) while the Vault is locked. Without a Tower login account these routes answer `409 account-required`. `POST /api/secrets/update` is gone. `POST /api/secrets/unlock {password}` stays the recovery password's unlock. Values travel only in these answers (`Cache-Control: no-store`), never into logs, ledgers or agent tools.

`server/auth/vault-password.ts` runs value-viewing unlocks, the recovery unlock, locks and the login change (`POST /api/auth/credentials`, refused with `403` for the master, local agents and run capabilities, and left out of the agents' route catalog) in one serial queue. A login change ends every grant, removes a candidate wrapper an earlier failed change left, prepares the new credentials, has the worker wrap the Vault key for them, writes auth.json (signing everyone out), and only then removes the other wrappers; a failure before the write leaves the login unchanged, and one after it at most leaves a harmless extra wrapper, so the credentials auth.json names always keep their wrapper while the Vault was open. The answer's `vault` is `rewrapped`, `locked` (the next unlock needs the recovery password once) or `unavailable` (no Vault, or an older worker). The worker serves these actions with the capability `secretValueView`; until it has it they answer `503 worker-update-pending` and nothing is sent to it.

Every turn in a session of this computer gets its own run-scoped secret MCP server (`server/api/run-tools.ts`), whoever started it: the owner, an agent, Slack, GitHub, a trigger or the master. Until a vault exists only the owner's own sessions get it, so a vault created during such a turn works there, and no other turn starts a broker process for nothing. `server/secrets/access.ts` decides the session's part again on each request. Public agents get none: a turn whose run or session comes from a public agent (a `public:` trigger), a native child of such a session, or a turn started with the calling credential of such a turn (`Run.delegation`, followed through each calling turn and its root). History keeps only the newest 100 finished runs, so a delegated turn keeps what its admission found (`delegation.publicChain`, inherited by its continuations): a calling turn that has since left history counts as checked when it is `false`, and `true` refuses for good; a record without it (an earlier version's, or a caller unknown at admission) is refused once its callers are gone, as before. Closed sessions and a joined computer's sessions mirrored on its controller, which use their own computer's broker, get none either. The tools confer no other Tower authority, and what each key may do still comes from its sharing, connections and exclusions. A new conversation's first turn gets the tools at once, since the provider fixes a turn's tools before the creation is confirmed; its secret requests wait until the session is confirmed.

The owner's own sessions are not reviewed: a session whose recorded provenance is the owner's, or a native conversation without provenance in which the owner starts a top-level turn. Every other use goes to the attack-only reviewer (`server/secrets/reviewer.ts`, model role `secrets.reviewer`): agent, Slack, GitHub and trigger sessions, native children, and any turn started with another turn's calling credential, even in the owner's own conversation. The review runs after the operation is claimed and its folder checked, before any value is resolved or file staged. It gets no tools: Tower gives it the request, the start of the script a run executes (credential files excluded) and the recent conversation, with common credential patterns masked as a best effort, never a value. It looks only for obvious abuse: a value sent to an outsider, Tower's vault or credentials taken, a plain bypass of Tower's limits. The whole review, waiting included, has 30 seconds, and two run at once. A block counts only with evidence quoted from that input. It becomes the operation's stored result (`SECRET_USE_BLOCKED` with its reason; a compare or fingerprint is refused as forbidden), so a retry with the same operation ID gets it back without a second review or consumer. The owner hears of each block once, with its reason and session, on the devices that want `runWaiting` notifications. A review that fails, times out or finds the reviewer busy allows the use and records `failed` with why. Refusals made by code (a locked vault, the wrong folder, a storage hold) stay refusals whatever the review says. A storage hold is refused by the broker alone, after the review and again inside the dispatch turn; during one the reviewer starts no model process, and its review just fails. Reviews count as worker work, so a handoff waits for them. Each use records how it was reviewed (`exempt`, `allowed`, `failed` or `blocked`); the chat's second tab shows each key's last one, and a reviewed session says that its uses are checked only for obvious abuse.

An instruction queued for a running turn is inserted only when it has the same origin and comes from the same calling turn (`Run.delegation`): delegated work never runs on an owner turn's unreviewed broker, and the owner's message does not join delegated work; the waiting message says so (`steerBlocked: 'delegation'`) and runs as its own turn. Tower's own notices to a turn (permission decisions, update wrap-ups) carry its origin and delegation.

The review is no guarantee. A model can miss an attack or be misled, the masking of its input is best effort, and it does not judge whether a use was wanted, only whether it is an obvious attack. The file a run executes is bound to the content an allowing review read: a script that changes before the run starts is refused rather than run on that review. A failed review binds nothing, since it would have allowed any script. A script larger than 16 MiB is neither read for the review nor bound to it, so it runs on the review's answer with no change check; one that was bound and grows past the limit before the run is refused.

Remote use requires an existing pinned Tower link **and** owner approval of each Vault's independent Ed25519/X25519 public-key fingerprint. Source A shares a key with B's sessions by GLOBAL (once B is a trusted node peer) or by B's folders, or the owner connects it to one of B's sessions from A's page, which starts that session's task on both computers. Automatic use enters a task on A only in a folder where something is allowed or the owner connected something. Both A and B must be unlocked. A's policy is checked for each signed request; signed, sealed responses bind the request and recipient. The relay holds opaque envelopes and B stores no permanent secret replica. B's session view asks A with a signed read-only `available` request, which A answers without a task or claim. B sends it only to a source whose relay confirmed, on a poll within the last 30 seconds, that its worker serves it (the poll header `x-tower-secret-features: available`, which the relay adds only while its worker has the capability `secretSharing`); it never falls back to `list`, which starts a task on A. A source whose relay polled within that window without the header runs an older build and is listed as waiting for an update (`updatePendingSources`); any other is listed as unavailable (`unavailableSources`). A's own view of B's session reads A's Vault for the folder, task and recent uses B reports (`/secret-session`, asked only of a computer advertising `secretSharing`). Remote tasks expire after eight hours, and locked/offline sources fail closed. B cannot edit/delete A's values. An unavailable remote close is reported, with source cleanup bounded by expiry; it never cancels the provider turn.

Vault initialization migrates the known legacy trigger-secret file through the encrypted store, preserving ID/origin/createdAt and the engine's trigger grants. Commit and verification precede plaintext unlink; after initialization there is no plaintext fallback or dual write. Backups include only the encrypted permanent Vault, never the runtime journal or temporary task payload. A legacy-only backup restored before Vault initialization keeps the existing worker restoration path. When either the source or target has a Vault, restore stages encrypted imports instead of replacing the target Vault: owner target unlock plus the **source Vault password** imports permanent records unshared, without copying source identity, trust, rules, sharing or connections. A deferred trigger snapshot and legacy trigger records are encrypted with the **backup passphrase**, so they may be a separate pending item requiring a different password. The trigger snapshot stays pending until referenced secrets can be validated; current trigger definitions are preserved until that point. A pending import is not reported as applied.

Fixtures live in `tests/server/secrets/`, `tests/server/auth/vault-password.test.ts` and `tests/server/backup/secrets.test.ts`. They cover ciphertext/KDF failures, restart lock, literal dotenv parsing, atomic failure recovery, selected fields, task/run isolation, TTL/revocation/sweep, sharing and rule decisions, folder canonicalization, side-effect-free views, authenticated transport and read negotiation, output masking, two encrypted runtimes and deferred trigger grants. Use fixture run registries and ordinary synthetic consumers; do not spawn native providers or scan personal session homes to verify secrets.
